# 按学习工具隔离并持久化对话记录

## 背景

学习空间左侧的工具列表用于切换不同的学习场景。当前前端只维护一份 `state.history`：点击工具后，标题和引导问题会更新，但右侧仍显示上一工具的对话。页面刷新后，全部对话也会丢失。

## 目标与范围

- 每个工具 `key` 拥有独立的对话记录。
- 切换工具时，右侧消息区、标题和快捷问题同步切换到该工具的状态。
- 记录在刷新页面后恢复。
- 本次仅在浏览器本地保存当前账号的对话；不新增服务端接口，也不实现跨设备同步。

## 设计

### 存储模型

用 `historyBySkill` 替代单一 `history`。其结构为：

```js
{
  culture_explorer: [{ role: "user", content: "..." }],
  speaking_partner: [{ role: "assistant", content: "..." }]
}
```

浏览器存储键由固定前缀、会话数据版本、当前账号的 `user_id` 和角色组成。这样同一浏览器中不同账号不会读取彼此的对话。写入失败或历史 JSON 损坏时，页面退回到空记录，不阻断对话功能。

### 交互与数据流

1. 页面初始化时读取 `localStorage`，并仅接受当前 `skills` 中存在的工具键和合法的用户/助手消息。
2. `setSkill()` 更新当前工具后，重新渲染该工具的消息区，同时更新工具选中态、标题、描述和快捷问题。
3. 发送时，将用户消息、流式完成后的助手消息追加到当前工具的数组；请求的 `history` 也只取当前工具的数组。
4. 每次追加、清空或停止后，将完整的 `historyBySkill` 写回本地存储。清空只清空当前工具，不影响其他工具。
5. 同一工具的流式请求尚未结束时禁止切换，以免响应写入错误的工具记录。

### 渲染边界

从持久化数据恢复的助手消息只渲染 Markdown 文本；不会恢复临时加载态、复制/保存操作按钮或回答来源卡片。这些附加 UI 只属于本次请求的即时响应，避免把短暂状态错误地持久化。

## 测试策略

- 抽出不依赖 DOM 的历史加载、过滤、按工具追加和序列化函数。
- 自动化测试验证：不同工具的消息互不混合；切换后读取正确数组；序列化再加载后完整恢复；损坏或不匹配的数据被安全忽略。
- 保留现有 Python 回归测试，并运行前端脚本的语法检查。

## 验收标准

1. 在工具 A 发送对话后切换到工具 B，右侧不显示工具 A 的消息。
2. 回到工具 A，右侧重新显示工具 A 的完整记录。
3. 刷新页面后，两个工具分别恢复各自的记录。
4. 清空工具 A 的记录不影响工具 B。
