# 按学习工具隔离并持久化对话记录

## 背景

学习空间左侧的工具列表用于切换不同的学习场景。当前前端只维护一份 `state.history`：点击工具后，标题和引导问题会更新，但右侧仍显示上一工具的对话。页面刷新后，全部对话也会丢失。

## 目标与范围

- 每个工具 `key` 拥有独立的对话记录。
- 切换工具时，右侧消息区、标题和快捷问题同步切换到该工具的状态。
- 记录在刷新页面后恢复。
- 本次仅在浏览器本地保存当前账号的对话；不新增服务端接口，也不实现跨设备同步。

## 设计

### 存储模型

用 `historyBySkill` 替代单一 `history`。其结构为：

```js
{
  culture_explorer: [{ role: "user", content: "..." }],
  speaking_partner: [{ role: "assistant", content: "..." }]
}
```

浏览器存储键固定为 `zhiyuqiao:chat-history:v1:<role>:<user_id>`。`role` 取 `boot.role`，缺失时使用现有脚本的默认值 `teacher`；`user_id` 必须是非空字符串。缺少 `user_id` 时不读写本地存储，页面仍以空记录正常工作。这样同一浏览器中不同账号不会读取彼此的对话。

加载时仅保留当前 `skills` 中存在的工具键，以及 `role` 为 `user` 或 `assistant`、`content` 为去除首尾空白后长度在 1 至 12,000 字符之间的消息。每个工具最多保留 20 条消息，且必须是完整的用户/助手成对记录；无效 JSON、无效消息和不完整的末尾记录一律忽略。写入失败时页面继续可用，不阻断对话功能。

### 交互与数据流

1. 页面初始化时读取 `localStorage`，并按上述规则过滤、裁剪与配对历史。
2. `setSkill()` 在非生成状态更新当前工具后，重新渲染该工具的消息区，同时更新工具选中态、标题、描述和快捷问题。
3. 发送前若当前工具已有 20 条记录，先移除最早的 1 个完整问答对；随后追加用户消息。请求的 `history` 始终只取当前工具，且不超过接口 `AssistantMessageRequest.history` 的 20 条上限。
4. 流式完成后追加助手消息。用户点击停止时，也追加一个助手消息：若已收到内容，则在其后标记「已停止生成」；若尚未收到内容，则使用现有的停止提示。这样每轮都能形成完整问答对并在刷新后如实恢复。
5. 每次追加、清空或停止后，将完整的 `historyBySkill` 写回本地存储。清空只清空当前工具，不影响其他工具。
6. `setSkill()` 在 `loading` 时返回失败；左侧工具列表与 `[data-skill-target]` 两个入口都必须以此结果为准，不得再更新主题、输入框或滚动位置。停止或请求结束后才允许切换，避免响应写入错误的工具记录或旧 DOM。

### 渲染边界

从持久化数据恢复的助手消息只渲染 Markdown 文本；不会恢复临时加载态、复制/保存操作按钮或回答来源卡片。这些附加 UI 只属于本次请求的即时响应，避免把短暂状态错误地持久化。

## 测试策略

- 抽出不依赖 DOM 的历史加载、过滤、按工具追加和序列化函数。
- 自动化测试验证：不同工具的消息互不混合；切换后读取正确数组；序列化再加载后完整恢复；损坏或不匹配的数据被安全忽略；第 11 个问答对会淘汰最早一对；停止时保存成对的已停止回答；生成期间的两个切换入口都不会改变当前工具。
- 保留现有 Python 回归测试，并运行前端脚本的语法检查。

## 验收标准

1. 在工具 A 发送对话后切换到工具 B，右侧不显示工具 A 的消息。
2. 回到工具 A，右侧重新显示工具 A 的完整记录。
3. 刷新页面后，两个工具分别恢复各自的记录。
4. 清空工具 A 的记录不影响工具 B。
